# Security & Secrets

How {{PROJECT_NAME}} handles secrets, what's safe to commit, and what isn't.

## TL;DR

| Item | Sensitive? | Where it lives | In git? |

## What's NOT actually secret

### Firebase web config

`firebase_options.dart` looks like a secret — it contains `apiKey`, `projectId`, `appId`. **It isn't.** Firebase web config values ship in every bundle of every Firebase app — anyone with the app can extract them in 30 seconds.

**Security comes from the Worker, not from hiding the config.** There is no client-to-database path: D1 is reachable only from `rust/api`. Every route must, in this order:

1. **Authenticate** — `auth::uid_from_request` verifies the Firebase ID token: RS256 signature against Google's published keys, expiry, `aud` = our project id, `iss` = `https://securetoken.google.com/<project id>`.
2. **Parse** into a typed `rust/shared` model that rejects unknown fields.
3. **Validate** with the model's `validate()`.
4. **Query** with bound parameters, scoped by the uid from the token (`WHERE uid = ?`).

If an attacker has the Firebase API key but no valid ID token, step 1 rejects every request. A valid token only ever reaches that user's own rows.

**The failure mode to watch for:** unlike Firestore rules (deny by default), a new route is public unless it calls `auth::uid_from_request`. A route that forgets step 1, or reads a uid from the request body or URL, is a data leak. `/d1` scaffolds routes correctly; review hand-written ones against this list.

**Critical:** `lib/firebase_options.dart` MUST be committed. Gitignoring it breaks CI with "No Firebase App '[DEFAULT]' has been created" — the file is generated by `flutterfire configure` and is part of the build.

### `flutter_dotenv` and `.env`

The `.env` file is loaded at runtime via `flutter_dotenv` — its contents are **bundled into the compiled app**. That means anything in `.env` is recoverable by anyone who has the app, exactly the same as `EXPO_PUBLIC_*` prefixed vars in React Native.

Treat `.env` as a config file, not a secrets store:
- ✅ Feature flags, URLs (privacy/terms/support), public API endpoints — all fine in `.env`.
- ❌ Anything that grants server-side privileges (admin tokens, server API keys, stripe secret keys) — never in `.env`. Those belong in Worker secrets (`npx wrangler secret put <NAME>`), read in Rust via `env.secret("NAME")`.

We gitignore `.env` for hygiene (each dev has different non-prod URLs), not because the values are secret.

### OAuth Client IDs

Client IDs are identifiers for the OAuth flow. They ship in client builds on purpose (in `Info.plist` URL schemes and `google-services.json`). The **client secret** (if used — token-based flows don't need one) WOULD be sensitive.

## What IS actually secret

### Cloudflare API token

A token with Workers + D1 edit rights can replace the API code and read or delete every row. Create it scoped to this account and these products only (dashboard → API Tokens → "Edit Cloudflare Workers" template), store it in Codemagic or your password manager, and rotate it if it ever lands in a log or a commit. Local work uses `npx wrangler login` (OAuth) — no token on disk.

### Worker secrets

Anything the Worker needs that grants privileges elsewhere (payment provider secret key, email API key):

```bash
cd rust/api
npx wrangler secret put STRIPE_SECRET_KEY     # production — encrypted, never readable back
echo 'STRIPE_SECRET_KEY=sk_test_...' >> .dev.vars   # local only — .dev.vars is gitignored
```

Never put these in `wrangler.toml` `[vars]` (plaintext, committed) or in the app's `.env` (bundled into the app).

### Firebase Admin service account

This stack does not need one — the Worker verifies tokens with Google's public keys. If you ever generate one for a one-off script, keep it outside the repo and delete it afterwards; it has full control of Firebase Auth users.

### Signing credentials

Codemagic manages iOS certs + Android keystores via its Code Signing UI. **Never** download to disk and commit. Locally, signing artifacts live in `~/Library/MobileDevice/Provisioning Profiles/` (iOS) and `~/.android/` (Android) — also outside the repo.

## Local `.env` pattern

- `.env.example` is committed (template, empty values)
- `.env` is gitignored (actual values)
- Move machines: copy `.env` manually (password manager / encrypted note). Never paste to Slack/email.

If you accidentally commit `.env`: rotate every value in it. Reality check: since none of the values are real secrets, an accidental commit is bad hygiene — not a breach.

## CI / deploy secrets

Codemagic stores env vars encrypted at rest. Add them via the dashboard, not via `codemagic.yaml`:

- `CLOUDFLARE_API_TOKEN` — only if CI deploys the Worker (see above for scoping)
- `APP_STORE_CONNECT_*` — API key for TestFlight/App Store publishing
- `GOOGLE_PLAY_SERVICE_ACCOUNT_CREDENTIALS` — JSON for Play Console publishing

For self-hosted CI (Gitea Actions / GitHub Actions): use repo secrets, reference as env vars in the workflow YAML.

## Threat model

{{PROJECT_NAME}} stores personal user data — not financial, not health-protected, not regulated. The threat model is: a malicious user trying to read/write *another user's* data. Mitigated by Firebase Auth + the Worker's per-route token check and uid-scoped queries. A leaked Firebase web config or D1 database id doesn't change the model. A leaked Cloudflare API token, Worker secret, or signing key WOULD — those are the actual secrets, and they live with Cloudflare / Codemagic, not in this repo.

Known gaps in the starter, to close before real traffic: no rate limiting on routes (add Cloudflare rate-limiting rules or Turnstile on abuse-prone endpoints); no App Check equivalent, so a valid user can call the API from outside the app (acceptable — the API only ever exposes that user's own data).

## Audit checklist (run before public launch)

- [ ] `git log --all -p -- .env` returns nothing
- [ ] Every route in `rust/api/src/` calls `auth::uid_from_request` first (only `/health` is public) and scopes SQL by that uid
- [ ] No hand-built SQL: `grep -n "format!" rust/api/src/` shows no query strings
- [ ] Tested against production with `curl`: no token → 401; expired token → 401; user A's token on user B's row id → 404
- [ ] `FIREBASE_PROJECT_ID` in `wrangler.toml` is the production Firebase project (a wrong id accepts another project's users)
- [ ] No secrets in `wrangler.toml` `[vars]`; `git log --all -p -- '*.dev.vars'` returns nothing
- [ ] Account deletion removes the user's D1 rows and R2 objects (test with throwaway account)
- [ ] No service account JSON in repo: `find . -name "*service-account*.json" -not -path "./.dart_tool/*" -not -path "./build/*"`
- [ ] No `package:http` imports outside `lib/core/api/` — API boundary intact
- [ ] Screenshots in store metadata contain no real personal data
